# 长任务接力（longtask-relay）

把长任务变成一条**会话链**：真理源落在工作区文件里，每个会话只承担一个阶段；上下文逼近上限时自动收尾、开新会话、交接，旧会话退役。侧栏面板监控每条链和每个会话。

## 安装

同事按仓库的插件索引安装，索引里的每个版本钉在一个具体的提交上：

1. 在 DSH 里打开「插件」，在「实验性插件」下打开「自定义插件索引」；
2. 切到「发现」标签页，点「添加索引源」，填入 `https://cdn.jsdelivr.net/gh/syncaus/dsh-plugins@main/market/index.json`（`raw.githubusercontent.com` 的同类地址在部分网络里连不上，DSH 会报「无法读取此索引」；镜像按 `@main` 缓存，发新版后可能延迟几分钟到几小时，要立刻拿到最新索引用 `https://ghproxy.net/https://raw.githubusercontent.com/syncaus/dsh-plugins/main/market/index.json`）；
3. 选「长任务接力」→「安装」，确认框里核对仓库、提交和目录。

更新方式是重新从索引装一次新登记的版本，不是 `git pull`。以 `link:` 装在本机 git 工作区的开发副本则相反：用面板或设置卡片里的自更新按钮（`git pull` + 重载插件）。

## 为什么需要它

DSH 自身的自动压缩（`compaction-basic`）能在上下文吃紧时把旧历史摘要掉，让会话继续跑；`goal-round-driver` 能让同一会话自动续轮。但压缩是有损的，反复压缩会让长任务越跑越差，而顶层会话之间没有父子关系，一个会话无法看到或接管另一个会话。

这个插件补的是中间那一步：**在压缩变成常态之前换一个干净的会话，并把「已经做到哪」交接过去**。

## 用法

在任意会话里让模型调用：

```
relay_start(objective: "把订单导出从 CSV 改成流式 XLSX，覆盖 3 个入口，全部有测试")
```

当前会话成为 `initializer`，必须先把真理源写出来：

```
<workspace>/.relay/<chainId>/
├── features.json   任务清单（既有条目的 id/title 不可改；新工作只能追加）
├── PLAN.md         链遵循的计划（计划模式批准过的计划原样写入；改动要同时在 decisions.md 写原因）
├── PROGRESS.md     Done / In progress / Next / Errors / Notes
├── HANDOFF.md      给下一个会话的短交接（开头是 <!-- relay:state --> 状态块）
├── history.md      交接历史：每次交接由插件自动追加上一份交接说明，可用 relay_recall 搜
├── decisions.md    决策台账（追加式：是什么 / 为什么 / 什么情况下算错）
└── traps.md        坑台账（追加式：踩过又费时间的坑，带具体命令或语法）
```

`features.json` 根部还放三条项目级命令，供所有条目引用：

| 字段 | 作用 |
|---|---|
| `statusCheck` | **对账命令**：把真理源里的说法和代码对一遍（解析路由 / 用例 / 迁移清单）。收尾与新会话启动都要跑它 |
| `verifyFast` | 每次收尾跑得起的快速校验收（秒级） |
| `verifyFull` | 完整校验，`relay_finish` 前跑 |

每条功能还带一个 `coverage` 字段，说明**验证到了多少**：`full`（端到端）、`partial`（只覆盖部分分支 / 平台 / 视口 / 子命令）、`smoke`（只证明它能响）。偏低的覆盖率默认不允许自动通过——必须由人在面板里点「接受」（模型工具不能写 `acceptedBy`）。

这三条命令和覆盖率取值都与技术栈无关：Rust 的 `cargo test`、Java 的 `mvn verify`、前端 `tsc --noEmit`、Python 的 `pytest -q` 都能当 `verifyFast`/`verifyFull`；输出被识别为证据的形态包括比例（`41/41`）、退出码（`exit 0`）、结论词（`ok`/`passed`/`BUILD SUCCESS`/`通过`）。

之后每完成一个功能，模型调用 `relay_checkpoint` 记录进度。会话空闲且上下文比例越过阈值时，插件先发一条收尾指令（做完当前单元、写进度、跑验证），下一轮空闲创建新会话并投递交接说明；新会话从真理源重建上下文，而不是复制旧对话。交接说明里带一份未完成功能的紧凑清单（id、标题、verify、files、deps），并要求只读 `HANDOFF.md` 的 `relay:state` 块和 `PROGRESS.md` 尾部；`decisions.md` / `traps.md` / `history.md` 用 `relay_recall` 检索，不整份读，`PLAN.md` / `features.json` 只在需要时读。交接时，退役链头名下仍未完成的功能会交回主线（审计记 `delegation.reclaimed`），新链头的「我的任务」能看到；已通过但挂在退役主线腿上的功能保留负责人，作为主线历史显示。每次交接，插件把上一份交接说明自动追加到 `history.md`。

**并行与续跑**：`relay_spawn` 把一部分功能交给子会话并行做；子会话上下文吃紧时，插件让它收尾并把未完成的功能交还链（清掉分配、写 PROGRESS），而不是只能压缩。父会话可以用 `relay_control(action="reclaim")` 随时收回。打开 `autoContinue` 后，链头空闲且没有 goal 驱动时会自动续跑下一个未委派的功能，超过 `maxAutoContinues` 记阻塞并暂停链。

交接前会检查 `HANDOFF.md` 是否新鲜：没有 `relay:state` 块、或内容还是当前会话接手时的那一份（按内容比对，不看文件时间，所以切分支、拷贝工作区不会被当成重写），就先收尾并给 `staleHandoffMinutes` 的宽限；仍不新鲜才交接，交接说明里会明确写"上一份已陈旧，以 PROGRESS / features / git 为准"。

**跨链冲突**：同一个工作区里可以并存多条链（例如把一个仓库拆成两条互不相干的推进线）。范围是文件级的：两条链的未完成功能声明了同一路径（含目录前缀）时，就可能同时改同一个文件。插件只报告、不替你选——`relay_status`、面板列表/详情/会话横幅会带上 `conflicts`（对方链、撞上的路径、双方的功能 id），`relay_checkpoint` 的返回值里也带同一份，模型能转告你。处理办法是先暂停其中一条链，或把功能改到不重叠的范围。只比较 `cwd` 完全相同的两条链：不同工作区（哪怕目录互相嵌套）不检测。

## 集群模式

先把需求和计划谈清楚，再由你决定开几个会话并行做。

1. 输入 `/relay cluster <需求>`，或直接说「开集群模式」。当前会话成为主会话并进入计划模式，链的状态是「规划中」。
2. 主会话和你谈需求，用计划评审把计划交给你。你批准后，它把需求写进 `SPEC.md`、计划写进 `PLAN.md`，并拆出功能清单；每个功能标出会改哪些文件（`files`）和依赖哪些功能（`dependsOn`）。
3. 主会话用 `relay_propose` 提交启动方案：分几组、每组领哪些功能、用共用目录还是 worktree、理由。它只能提方案，不能自己开会话。
4. 启动方案有两个确认入口：主会话的输入框上方会出现「启动方案已就绪」启动条（点「启动 N 个并行会话」，再点一次确认）；面板里这条链的「启动方案」卡片顶部也有同一个按钮（点一次变「确认启动」）。面板里还可以把功能改到别的组、新建一组、留给主会话，或改隔离方式；两个共用目录的组文件范围重叠时，卡片上方会提示。也可以输入 `/relay launch`。
5. 各会话做完用 `relay_checkpoint` 回报，主会话复验后结束链。每个会话可以用 DSH 的子代理工具把自己的功能再拆开做。

几条规矩：

- 某一组依赖的功能不在任何组里、且还没通过时，这一组先不开，记为「待启动」；前置功能通过后插件自动把它开出来。常见用法是把地基功能留给主会话先做。
- 依赖关系跨了两个组的方案会被拒绝：有依赖的功能放进同一组按顺序做。依赖了不存在的功能同样被拒绝。
- 冲突提示也算上主会话自己要做的活：标成 worktree 的组和没进任何组的功能都由主会话在同一个目录里做，和共用目录的组文件范围重叠时一样会提示。路径比较不分大小写，`./` 开头和工作区下的绝对路径按同一个位置算；`.` 表示整个工作区，和任何范围都算重叠。面板里的冲突、拒绝原因和「待启动」提示都由引擎按你当前的分组现算。
- 功能清单在启动那一刻冻结。规划阶段可以反复改清单、重新提交方案；启动之后再手改功能的 id 或标题会被拒绝。
- 本期只有共用目录真正并行。方案里标成 worktree 的组不开会话，功能由主会话顺序做。
- 规划中的链不参与自动交接，也不能暂停；规划时记的阻塞只显示、不改状态，但有未解除的阻塞时不能启动。离开「规划中」只有两条路：启动，或删除这条链。
- 开启 `clusterGoals`（默认开）时，启动会给主会话和每个子会话各建一个 goal，子会话不会跑一轮就停。子会话的 goal 跟着它的活走：手上没有未完成的功能、或链处于暂停时，它被暂停；链恢复运行且它还有活时恢复（只恢复插件暂停的，你手动暂停的不动）；链结束时标为完成；会话重新加载后恢复一次续行。子会话没加载时不处理，加载后补上。
- 链头交接后仍然是一条集群链：新链头接手监督。`clusterGoals` 开着时会按 `goalRoundsPerHandoff` 给新链头建一个 goal（不受 `seedGoalOnHandoff` 限制），交接提示词会列出仍在跑的 worker 和它们未完成的功能，并要求复跑 verify；新链头的「下游」页签列出整条链的 worker（包括前任链头派出的）。worker 有功能通过时会收到一条 `<relay_worker_report>` 提醒去验收；只写进度、没有功能转通过的 checkpoint 不会打扰链头。worker 会话本身不会消失，也不重新洗牌。

## 工具

| 工具 | 作用 |
|---|---|
| `relay_start` | 开始一条链，当前会话成为 initializer；`mode: "cluster"` 以集群模式开始 |
| `relay_propose` | 集群模式下提交启动方案（分组、隔离方式、理由），等人确认 |
| `relay_status` | 紧凑读出所有链的状态、进度、当前会话和在跑的 worker；退役腿只给计数，完整轨道看面板 |
| `relay_checkpoint` | 更新功能状态 / 证据 / 覆盖率，追加发现的新功能，记录阻塞，标记 `ready` |
| `relay_audit` | 读链的审计日志；默认 20 条、detail 字符串截到 300 字符，`full=true` 取原文 |
| `relay_recall` | 按关键词检索链内记忆（PLAN / HANDOFF / history / PROGRESS / decisions / traps / features / audit） |
| `relay_finish` | 结束链；功能没全部通过时会被拒绝并列出剩余项 |
| `relay_spawn` | 把一部分功能交给新的子会话并行执行（仅链头会话可调用） |
| `relay_control` | 暂停 / 恢复自动接力、立即交接，或收回某个 worker 的未完成功能（`reclaim`）；删除链只保留在面板 |

## 斜杠命令

| 命令 | 作用 |
|---|---|
| `/relay` | 列出各条链，并指出当前会话属于哪条 |
| `/relay start <目标>` | 在当前会话开始一条链（等价于 `relay_start`） |
| `/relay cluster <需求>` | 以集群模式开始：先规划，再由你确认并行启动 |
| `/relay launch` | 按已提交的启动方案开出各组会话（等价于输入框上方的启动条和面板的「启动」） |
| `/relay pause` / `/relay resume` | 暂停 / 恢复当前会话的链；效果与面板按钮一致 |
| `/relay handoff` | 立即交接一次，效果与面板按钮一致；会话还在跑时会拒绝 |

命令不经过模型，直接由 Host 执行。

## 更新

插件以 `link:` 方式装在 git 工作区里，所以“有新版本”直接看 git 上游：打开面板时比较本地 HEAD 与上游分支，落后时右上角显示「更新到 vX」，没有落后则显示当前版本号。

点击更新会执行 `git pull --ff-only`，然后禁用/启用一次本插件，让 Host 加载新代码。工作区有未提交改动时拒绝更新（避免覆盖本地修改）；没有上游分支或不在 git 里时只显示版本号，不提示更新。

## 部分验证的人工接受

`finish` 要求每条通过的功能要么 `coverage: full`，要么被人工接受。面板的「接受」/「接受全部」会把 `acceptedBy` 写成 `human` 并打上 `acceptedAt` 时间戳；手工编辑 `features.json` 写 `acceptedBy: "human"`（没有时间戳）不会被认可，必须从面板接受一次。结束链被拒不只报第一条阻塞：未通过、证据不足、部分验证未接受会一起列出。

## 面板

三个页面是同一份数据的三个范围，互相可以跳转：

- 侧栏「长任务接力」：顶部切换「任务链 / 最近删除」；任务链页最先显示「需要你处理」（等待审批 / 回答的会话、被阻塞的链、出错的链），左侧是链列表（模式：集群 / 单任务、状态或收尾 / 交接阶段、进度、交接次数、峰值上下文；规划中、等你确认启动的集群会额外标出「等你确认启动」），右侧是选中链的详情：接力轨道（主线会话按交接顺序排开，子会话挂在派发它的那一棒下面，每棒显示上下文占用、峰值、压缩次数、退役原因，点击打开会话）、功能清单（验证命令、证据、负责会话，可按通过状态筛选）、真理源文档（交接说明、进度、交接历史、决策、踩坑）和审计记录，以及暂停 / 恢复 / 立即交接 / 调高交接上限（链因交接次数到顶暂停时出现；删除在详情底部的危险操作区）；部分验证的功能可以在这里点「接受」。暂停的链会写明原因（手动、阻塞、交接失败、交接次数到顶）。只有人能解决的阻塞，做完后点「已处理，解除阻塞」即可让链继续（来自被阻塞 goal 的阻塞要在对应会话里恢复 goal）；功能全部通过后可以在这里填一段验证说明直接结束链，Host 仍会按 `relay_finish` 的规则复核；子会话卡住时可以「收回」它没做完的功能；真理源里可以按关键词搜索链内记忆（与 `relay_recall` 同一套检索）。交接要在原位再点一次确认；删除会先展开后果清单：链目录（功能清单、进度、交接说明、审计）移入 `.relay/.trash/`，可以在面板顶部的「最近删除」页里恢复，恢复后保持暂停，也可以永久删除；删除入口放在详情底部的「危险操作」区，不和暂停/交接混在一起。会话和 goal 不会删除，goal 会先暂停（会话当时没加载的话，下次打开时暂停）；进行中的链要先暂停，链里还有会话正在运行时不能删除。会话的「下游」/「我的任务」会显示原链已删除，而不是引导重新 `relay_start`。
- 会话标签「下游」（本会话派发出去的）：每个子会话的状态、上下文占用、负责的功能和通过情况、goal 阶段。
- 会话标签「我的任务」（本会话接到的）：本会话在链里的位置（主线 / 子会话、上级会话、是否已交接给下一棒）、负责的功能，以及当前 goal 的阶段、轮次和是否会自动继续。主线会话负责的是没有派给子会话的功能，也包括前任主线腿留下的已分配项（负责人会标出来）；子会话只看自己领到的功能。

两个会话标签顶部都显示所属的链，「在面板中查看」跳到面板并选中这条链。

集群链还在规划、且主会话已提交启动方案时，主会话的输入框上方会出现「启动方案」启动条：显示组数、功能数、每组标题和启动后开几个会话，按钮是「启动 N 个并行会话」（点一次变「确认启动」）。它在对话里就能完成启动，按的是主会话已提交的方案；要改分组就用旁边的「调整分组」跳到面板。面板里同一个启动按钮在链路详情「启动方案」卡片顶部，不在分组列表底部。

「需要你处理」里的「等你确认启动」会跳到这条链，动作按钮是「去启动」。

链列表的状态有三种在看：**运行中**（链头正在生成）、**空闲**（真的没人在跑）、**后台运行**（链头这一轮结束了，但它起的后台作业还在跑）。第三种最容易被误读成停住，所以卡片上还会标出作业数，悬停能看到作业标签；`relay_status` 里对应 `jobs` 字段，`/relay status` 也会写出来。

## 配置

在 profile 的 `cordis.patch.yml` 里覆盖：

```yaml
- id: longtask-relay
  name: 'dsh-longtask-relay'
  config:
    handoffRatio: 0.70
    wrapupRatio: 0.50
    maxHandoffs: 32
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `truthDir` | `.relay` | 真理源目录，相对工作区 |
| `autoHandoff` | `true` | 是否允许自动交接 |
| `wrapupRatio` | `0.50` | 进入收尾的上下文比例（留一半窗口给收尾本身） |
| `handoffRatio` | `0.70` | 收尾后仍到这个比例就强制交接；**必须低于 `compaction-basic` 的 `thresholdRatio`** |
| `handoffAfterCompactions` | `1` | 压缩过几次后，低比例也触发收尾 |
| `compactedRatioFloor` | `0.50` | 配合上一项的比例下限 |
| `hardCompactions` | `2` | 压缩达到几次后不等边界直接交接 |
| `maxHandoffs` | `32` | 单链交接上限 |
| `cooldownMs` | `5000` | 同一会话两次判定之间的最小间隔 |
| `wrapupTimeoutMinutes` | `10` | 收尾后空闲多久仍然强制交接 |
| `staleHandoffMinutes` | `5` | 收尾后多久内必须写出新鲜的 HANDOFF；到期仍陈旧就带着警告交接 |
| `stallMinutes` | `15` | 链头一直在跑、却这么久没写过真理源时，面板和 `relay_status` 标出「N 分钟无进展」（多半卡在一条长命令或后台作业里）；只做提示，不暂停、不交接 |
| `autoContinue` | `false` | 链头空闲且无 goal 驱动时，自动续跑下一个功能；`autoHandoff` 关闭时不生效 |
| `maxAutoContinues` | `20` | 每个会话自动续跑的次数上限，到顶记阻塞并暂停 |
| `commitTruth` | `true` | 收尾/初始化提示里是否要求提交真理源；关掉只记录 sha256 |
| `agentPreset` | 空 | 新会话使用的 preset；空表示继承当前会话 |
| `inheritPermission` | `true` | 接力会话和子会话沿用上一个会话的权限预设（沙箱模式 + 审批策略，例如完全权限）；关掉后新会话用 DSH 设置里的默认预设。上一个会话是自定义组合（不对应任何预设）时不继承 |
| `workerApproval` | `never` | 继承预设之后再覆盖审批策略：`inherit` 不覆盖；`ask` 每次询问，无人值守时会一直等；`never` 不询问，需要升级权限的操作直接失败并记为阻塞 |
| `pauseGoalOnRetire` | `true` | 交接后暂停旧会话的 goal |
| `seedGoalOnHandoff` | `false` | 交接后给新会话建一个 goal，让目标轮驱动继续跑；需要目标服务可用。集群链的链头例外：`clusterGoals` 开着时，交接总会给新链头建 goal |
| `goalRoundsPerHandoff` | `16` | 给新会话 goal 分配的续轮上限 |
| `inheritGoal` | `true` | 交接时新会话沿用你自己建的 goal，轮次只给剩余部分（上限减已用轮次），整条链共用一份轮次预算；插件按 `seedGoalOnHandoff` 建的 goal 不继承；关掉后不继承 |
| `rearmGoalOnReload` | `true` | Host 重启或插件重载后，恢复本插件建的 goal 的自动续行；用户自己建的 goal 不动 |
| `maxClusterSessions` | `4` | 集群模式一次启动最多分几组 |
| `clusterGoals` | `true` | 集群启动时给主会话和每个子会话各建一个 goal；集群链交接时也给新链头建一个 |
| `inheritPlanMode` | `true` | 旧会话处于计划模式时，接力会话和子会话也以计划模式启动 |
| `notifyOldSession` | `true` | 交接后给旧会话留一条退役说明 |
| `pauseOnExternalBlocker` | `true` | 遇到「只有人能解」的阻塞（`kind=external`）时暂停该链 |
| `requireStrongEvidence` | `true` | 通过的功能是否必须带「像命令结果」的证据；输出是自由文本的项目可关掉 |
| `requireHumanAcceptedCoverage` | `true` | 低覆盖率是否必须由人确认；把部分覆盖当常态的项目可关掉 |

**重要**：两个比例分工不同 —— `wrapupRatio`（默认 0.50）开始收尾，`handoffRatio`（默认 0.70）在收尾之后仍然到点就强制交接；前者必须小于后者，配置校验会拒绝反过来的组合。`compaction-basic` 默认在上下文窗口的 0.8 处压缩，如果它先压缩，压力会被降到很低，本插件就不会触发。请保证 `handoffRatio < compaction.thresholdRatio`（默认 0.70 < 0.80），或者把压缩阈值调到 0.9、把 `handoffRatio` 调到 0.78。

## 证据与阻塞的规矩

- **`passes` 必须有可用证据**：`evidence` 里要出现命令、退出码或计数。`relay_finish` 会拒绝「通过但证据不足 8 个字符或缺数字」的条目；`relay_checkpoint` 在写入 `passes=true` 时先挡一道（`evidence_too_weak`）。
- **数字不许手写**：真理源里的计数必须来自 `statusCheck` 的输出引用，否则下一棒会把过时数字当事实。
- **阻塞分三类**：`external`（等人：账号、机器、只有 owner 能做的决定）、`code`（等自己修）、`decision`（等一个选择）。`external` 会暂停链并写下「谁要做哪件事才解开」，避免继续开新会话空转；链头的 goal 会随链一起暂停，否则目标轮会绕过暂停继续给会话发指令。面板解除阻塞时一并恢复这个 goal。
- **与桌面端目标功能的关系**：目标（goal）管一个会话内的自动续轮，接力管换会话，两者串行互补。开启 `seedGoalOnHandoff` 后，交接会给新会话按链目标和当前进度建一个 goal，新会话由目标轮驱动继续，而不是跑完交接说明就停住。反过来，链头会话的 goal 进入 `blocked` 时（例如轮次耗尽），链会被记为 external 阻塞并暂停；在目标条里恢复或清除 goal 后，链的这条阻塞会立即解除（不再等下一次空闲评估），恢复链时也会马上核对 goal 并清理这类过期阻塞。对插件按 `seedGoalOnHandoff` 建的 goal，把 `pauseOnExternalBlocker` 关掉时只记录阻塞、继续交接，让新会话重新拿到轮次预算。
- **发现新工作只能追加**：`relay_checkpoint` 的 `addFeatures` 需要 `reason`，追加动作会写进 `PROGRESS.md`，让「初始化时没想到」这件事留下痕迹。

## 与目标模式、计划模式的配合

- 收尾指令发出后和交接开始时，插件会取消旧会话 goal 的自动续行（只取消续行，goal 本身的阶段不变），避免旧会话在收尾后又被目标轮推着继续干活，或在新会话已经启动时多跑一轮。
- 交接时新会话继承旧会话的 goal：你自己建的 goal 会被继承，目标不变、轮次只给剩余部分；本会话显示的是它拿到的剩余额度。旧 goal 轮次用完时不继承，链记一条阻塞等你处理。插件按 `seedGoalOnHandoff` 建的 goal 不继承，每次交接照旧按 `goalRoundsPerHandoff` 新建；集群链例外：`clusterGoals` 开着时，即使 `seedGoalOnHandoff` 是关的，交接也会给新链头建 goal，否则没人验收 worker。你的 goal 处于阻塞或被你暂停时，不会被换成新建的 goal；阻塞的 goal 在交接后还会留下一条阻塞，等你处理。`inheritGoal` 关掉后回到 `seedGoalOnHandoff` 的旧行为（集群链仍按 `clusterGoals` 建链头 goal）。
- 本插件建的 goal 在 Host 重启或插件重载后会被恢复自动续行；用户自己建的 goal 不动。链用 `relay_finish` 结束时，本插件建的 goal 一并标为完成。
- 在面板里暂停一条链会同时暂停链头会话的 goal，恢复链时把这个 goal 一并恢复；会话自己调用 `relay_control` 暂停链不动 goal。
- 旧会话处于计划模式时，接力会话和子会话也以计划模式启动。
- 计划模式下 `relay_start` 会被拒绝：先把计划做完并批准，再开链。批准后的计划写进 `PLAN.md`，`features.json` 据此拆分。
- 面板和两个会话标签页会标出处于计划模式的会话；链详情的「目标」一行显示当前会话 goal 的阶段、轮次用量，以及续行是被插件暂缓（等待交接）还是随链暂停。

## 已知限制

- 顶层会话之间没有父子关系，链结构完全由插件记录；手动归档会话会让链出现悬空引用。
- 新会话会重新支付一遍 system prompt 与工具 schema 的成本。
- 「功能是否真的通过」由 `features.json` 的 `passes` 与 `evidence` 约束，插件不能代替验证；插件只校验证据的形状，不校验它是否真实。
- 未加载的会话没有实时上下文数值，面板显示「未加载」。
- 一个 Host 进程内的运行态不跨进程共享：峰值压力、判定冷却、交接中的忙标记。压缩次数、收尾时间、`ready` 和链结构都持久化在链文件里，重启或重载后恢复，不会重复收尾。
- 委派给 subagent 的调用会被工具拒绝。
- 集群模式本期只有共用目录并行，worktree 隔离与合并还没做；规划阶段不参与自动交接，规划对话特别长时靠 `SPEC.md` / `PLAN.md` 落盘兜底；子会话上下文吃紧时沿用子会话的既有行为，把没做完的功能还给链。
