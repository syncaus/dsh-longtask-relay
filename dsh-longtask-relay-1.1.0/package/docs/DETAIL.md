# 长任务接力

## 它解决什么

一个长任务跑久了，上下文一定会满。DSH 的自动压缩会把旧历史摘要掉，让会话继续，但摘要是有损的：细节被压平、决策理由被丢掉，越往后越容易在同一个问题上反复。而顶层会话彼此独立，`list_agents` / `send_message` 只覆盖 subagent 树，一个会话看不到另一个会话在做什么，也无法把自己没做完的事交出去。

这个插件用「会话链」补上这段：一个任务对应一条链，链上有多个会话，同一时刻只有一个链头在推进；需要并行时链头可以委派 worker 各做一部分，worker 上下文吃紧会把未完成的功能交还链。上下文逼近上限时，当前会话先收尾（做完当前最小单元、写进度、跑验证），插件再开一个干净的新会话，把「真理源在哪里、做到第几步、下一步做什么」交给它。旧会话退役，不再自动工作。

## 真理源

链的全部长期记忆在工作区里：

```
<workspace>/.relay/<chainId>/
├── features.json   任务清单，JSON（根部含 statusCheck / verifyFast / verifyFull）
├── PLAN.md         链遵循的计划；计划模式批准过的计划原样写入，改动须同时在 decisions.md 记原因
├── PROGRESS.md     Done / In progress / Next / Errors / Notes
├── HANDOFF.md      给下一个会话的短交接（≤ 60 行，开头是 relay:state 状态块）
├── history.md      交接历史：插件每次交接自动追加上一份 HANDOFF 全文
├── decisions.md    决策台账，追加式
├── traps.md        坑台账，追加式
└── relay.json      插件维护的链元数据：会话列表、交接次数、状态、当前 blocker
```

`features.json` 的每条记录：

```json
{
  "id": "F001",
  "title": "登录接口返回 401 时前端跳转登录页",
  "priority": 1,
  "passes": false,
  "evidence": null,
  "verify": "pnpm test auth/redirect.spec.ts",
  "coverage": "full",
  "acceptedBy": null,
  "notes": ""
}
```

既有条目的 `id`、`title` 不可改，会话只能改 `passes`、`evidence`、`coverage`、`acceptedBy`、`notes`——否则「完成」的定义会被会话自己改写。这条约束由 `relay_checkpoint` 强制执行，`relay_finish` 在还有未通过条目、证据不足、或覆盖率偏低且没人确认时都会拒绝。

**发现新工作时**用 `relay_checkpoint` 的 `addFeatures`（追加，附 `reason`）。初始清单再用心也一定会漏：子系统、依赖、环境限制往往做到一半才浮出来。追加会写进 `PROGRESS.md`，让「当初没想到」这件事留下痕迹，同时不允许借机删条目或改标题。

### 三条项目级命令与两类台账

- `statusCheck`：把真理源里的说法和代码对一遍。它是**反漂移闸门**——手工累加的计数迟早会和代码不一致，交接时被当成事实引用。
- `verifyFast` / `verifyFull`：收尾跑前者，`relay_finish` 前跑后者。三条命令都来自项目自身，插件不假设语言或构建工具。
- `decisions.md`：每一个会改变交付物的判断（跳过某项、接受一处差异、某个取舍）都记「是什么 / 为什么 / 什么情况下算错」。下个会话据此不再重开讨论，也不会好心把它「修」掉。
- `traps.md`：踩过又费时间的坑，附确切命令或语法。同一类坑踩第二次的成本比写一条记录高得多。

### 阻塞分三类

| kind | 含义 | 插件行为 |
|---|---|---|
| `external` | 只有人能解（账号、机器、权限、只有 owner 能做的决定） | 链置为 `paused`，写下「谁、要做什么」，停止自动交接 |
| `code` | 自己修 | 只记录，链继续 |
| `decision` | 等一个选择 | 只记录，链继续 |

覆盖率 `coverage` 同理与项目类型无关：`full` / `partial` / `smoke` 描述的是**验证的深度**，不是某种测试技术。API 里只验了拒绝分支、UI 里只验了一个视口、CLI 里只验了一个子命令，都属于 `partial`。

外部阻塞如果不暂停，链会按压力继续开新会话，把交接预算烧在「换个会话再确认一次还是被挡住」上。

## 一次交接发生什么

1. 会话空闲且上下文比例越过 `handoffRatio`（或压缩次数达到 `handoffAfterCompactions`）。
2. 插件注入一条收尾指令：做完当前功能、重写 `PROGRESS.md`、跑一次验证、重写 `HANDOFF.md`，不要开始新功能。
3. 收尾轮结束、会话再次空闲（或模型调用 `relay_checkpoint(ready=true)`；`ready` 要求 `HANDOFF.md` 里已经有 `relay:state` 块，并且内容不再是本会话接手时的那一份，否则被拒绝，避免空交接或把上一棒的说明原样交下去）。
4. 插件创建新会话：同一工作目录、同一 preset，命名成「任务 · 接力 N」，加入同一工作区。
5. 投递交接说明：目标、链 id、交接序号、真理源绝对路径、当前进度、下一件事、热身步骤（读三份文件、跑验证）、以及「一次只做一个功能」的规则。开启 `seedGoalOnHandoff` 时，还会按链目标和当前进度给新会话建一个 goal，交给目标轮驱动继续。
6. 旧会话收到退役说明，其 goal 被暂停，不再参与判定。插件同时把旧会话写的 `HANDOFF.md` 全文追加到 `history.md`（带会话 id、交接原因、时间），所以更早的交接不会因为 `HANDOFF.md` 被覆盖而丢失；新会话用 `relay_recall` 按关键词检索这些历史，而不是全量读。

与目标模式、计划模式的关系：收尾指令发出后和交接开始时，插件取消旧会话 goal 的自动续行，防止旧会话在收尾后继续被目标轮驱动。新会话继承旧会话的 goal，轮次只给剩余部分（`inheritGoal`），没有剩余轮次就不继承；本插件建的 goal 在重启后恢复续行（`rearmGoalOnReload`），`relay_finish` 时标为完成，面板暂停 / 恢复链时同步暂停 / 恢复它。旧会话处于计划模式时新会话也以计划模式启动（`inheritPlanMode`），而计划模式下不能 `relay_start`，批准后的计划写进 `PLAN.md`。

链头会话的 goal 如果进入 `blocked`（例如轮次耗尽），插件把它记成 external 阻塞并暂停链；在目标条里恢复或清除 goal 后，这条阻塞会自动解除。`pauseOnExternalBlocker=false` 时只记录阻塞、继续交接，让新会话拿到新的轮次预算。

交接说明只给路径和短摘要，不复制对话内容——让新会话从文件重建，而不是继承旧噪音。

## 什么时候会触发

| 条件 | 动作 |
|---|---|
| 上下文比例 ≥ `wrapupRatio`（默认 0.50） | 进入收尾 |
| 成功压缩 ≥ `handoffAfterCompactions` 且比例 ≥ `compactedRatioFloor` | 进入收尾（压缩过说明吃紧过） |
| 成功压缩 ≥ `hardCompactions`（默认 2） | 不等边界直接交接；若 HANDOFF 陈旧则先收尾 |
| 已收尾，且 `ready=true` / 比例 ≥ `handoffRatio`（默认 0.70）/ 空闲超 `wrapupTimeoutMinutes` / 陈旧宽限到期 | 交接（陈旧时交接说明带警告） |
| 链头空闲、无 blocker、无 goal 驱动且 `autoContinue` 开启 | 续跑下一个未委派功能，超过 `maxAutoContinues` 记阻塞 |
| worker 上下文比例 ≥ `wrapupRatio` 或压缩达到 `hardCompactions` | 让它收尾并交还未完成的功能 |

判定只在会话**完全空闲**（没有排队的下一步输入）时进行，所以不会打断正在输入的人类。每次判定之间有 `cooldownMs` 冷却；被冷却挡掉的判定会补一次，收尾后还会挂一个 `wrapupTimeoutMinutes` 的到期重评，插件重载时会按持久化的 `wrapupAt` 重新挂上。

## 与自动压缩的关系

`compaction-basic` 默认在窗口的 80% 处压缩。压缩之后压力会掉到很低，本插件看起来就「不该触发」了。所以强制交接线必须低于压缩线：默认 `handoffRatio` 0.70。如果你把压缩阈值调到 0.9，可以把 `handoffRatio` 调到 0.78，给收尾轮留出余量。

## 面板

侧栏的「长任务接力」列出这个 Host 已知的每条链：状态（或正在收尾 / 等待交接的阶段）、功能进度、交接次数、峰值上下文。需要人处理的事（等待审批或回答的会话、被阻塞的链、出错的链）集中在顶部。选中一条链可以看到它的接力轨道：主线会话按交接顺序排开，子会话挂在派发它的那一棒下面，每棒显示角色、是否在线、上下文占用与峰值、压缩次数和退役原因；下面是完整的功能清单、真理源文档（交接说明、进度、交接历史、决策、踩坑）和审计记录。按钮可以暂停/恢复自动交接、立即交接一次、调高交接上限（链因次数到顶暂停时出现），或删除这条链；删除只对暂停、完成、失败的链开放，会连链目录（功能清单、进度、交接说明、审计）一起删掉。交接和删除都要在原位再点一次确认。

会话里的「下游」标签页列出本会话派发的子会话，「我的任务」标签页列出本会话在链里的位置和它负责的功能；两者都能跳回面板里的这条链。

面板数据每 5 秒从 Host 重新读取；会话的压缩次数来自一个每会话的投影，所以即使会话没被打开也能看到。

## 限制

- 链结构由插件记录，DSH 本身不维护顶层会话之间的关系。
- 新会话要重新付一遍 system prompt 和工具 schema 的成本。
- 未加载的会话没有实时上下文数字。
- 插件重启后按 Host 级索引列链（`~/.dsh/longtask-relay/index.json`）；链文件已被删掉的索引条目会被跳过。
- 一个 Host 进程内不同步到其他进程。
- 委派的 subagent 不能操作链。
