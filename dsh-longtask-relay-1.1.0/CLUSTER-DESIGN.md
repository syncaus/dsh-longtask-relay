# 集群模式设计（第一期）

状态：已批准，第一期已实现到单测与面板预览，闭环实跑未做（见「验证方式」）。标「按推荐」的条目是需求方认可方案 A 后由实现方裁定的。

## 要解决什么

现在的接力链是「一个会话干到上下文快满，换下一个会话」。并行只有 `relay_spawn`：由模型在执行中自己决定派不派，人插不上手，也没有「先把需求和计划谈清楚」这一段。

集群模式给主会话加两段：

1. **规划段**：主会话和人谈需求，写 spec，定计划和目标，拆功能清单。不动业务代码。
2. **启动段**：AI 给出启动方案（开几个会话、各领哪些功能、各用什么隔离方式、理由），人确认或修改后，插件一次开出这些会话并行执行。每个会话可以按情况自己开子代理。

## 目标与非目标

**目标**
- 规划和执行分开，执行必须由人确认后才开始。
- 并行度和分组由 AI 推荐、人决定。
- 复用现有的真理源、功能清单、子会话派生、面板、权限/目标/计划模式继承。

**第一期不做**
- git worktree 隔离与合并（第二期）。第一期 AI 仍可推荐 worktree，面板标明「本期改为主会话顺序执行」。
- 子会话自己的接力（子会话上下文吃紧时沿用现有行为：把没做完的功能还给链）。
- 启动后再追加一批并行会话的界面（主会话仍可用现有的 `relay_spawn`）。

**反目标**
- 模型不经人确认自己开出一批会话。
- 两个共用目录的会话被分到会改同一批文件的功能，而界面没有提示。

## 做法比较

| 做法 | 结论 |
|---|---|
| A. 在接力插件里加规划段和启动步骤 | 采用。现有能力直接复用，新增的只是前段和启动这一步 |
| B. 建在 DSH 团队模式上 | 不采用。成员是同一会话树里的子代理，不是能单独打开的对话；只能共用目录；开关在模型菜单里，插件接不到「人来选」这一步 |
| C. 单独写一个新插件 | 不采用。链存储、面板、交接逻辑要再抄一遍，两个插件会抢同一批会话 |

## 流程

```
/relay cluster <需求>        链状态 planning，主会话进入计划模式
  │  谈需求 → exit_plan_mode 交计划 → 人在 DSH 的计划评审里批准
  │  写 SPEC.md、PLAN.md、features.json（每个功能带 files、dependsOn）
  ▼
relay_propose                AI 提交启动方案：分组、隔离方式、理由
  ▼
启动条 / 面板卡片             人点「启动 N 个并行会话」，两步确认；改分组去面板卡片
  ▼
插件开出各组会话              链状态 active；主会话收到监督说明
  ▼
各会话 relay_checkpoint 回报 → 主会话验收 → relay_finish
```

## 设计

### 入口

- `/relay cluster <需求>`：人的入口。
- `relay_start` 工具加可选参数 `mode: "cluster"`：人用自然语言说「开集群模式」时模型走这里。（按推荐）

两者都调 `engine.startCluster`。它和 `start` 的差别：
- 不因计划模式拒绝；相反，`planMode` 服务可用时把会话切进计划模式。服务不可用时照常继续，靠规划提示词约束「不改业务代码」。
- 链记录写 `mode: 'cluster'`、`status: 'planning'`。
- 骨架多一份 `SPEC.md`。
- 发规划提示词（`renderClusterPlanningPrompt`），不发初始化提示词。

### 规划提示词要求模型做的事

1. 先和人把需求谈清楚，不动业务代码。
2. 用 `exit_plan_mode` 交计划，等人批准。
3. 批准后写 `SPEC.md`（需求与验收标准）、`PLAN.md`（批准的计划原文）、`features.json`。
4. 每个功能除现有字段外，写 `files`（它会改的文件或目录，路径前缀）和 `dependsOn`（依赖的功能 id）。
5. 调 `relay_propose` 提交启动方案，然后停下等人确认，不调用 `relay_spawn`。

推荐规则写进提示词：文件范围不重叠的功能可以分到不同的共用目录会话；范围重叠、或各自要跑完整测试的，推荐 worktree；有依赖关系的放同一组按顺序做；主会话自己留一组也可以。

### 功能清单新增字段

`files: string[]`、`dependsOn: string[]`，都可缺省。`chain-store.js` 的规范化和 `appendFeatures` 保留这两个字段。它们不参与冻结指纹之外的任何既有判断。

### `relay_propose`（模型调用）

参数：`groups: [{ title, features: [id], isolation: 'shared' | 'worktree', reason }]`，可选 `note`。

拒绝条件：
- 调用者不是链头，或链不是 `planning`。
- 会话仍在计划模式（计划还没被批准）。
- 组数超过 `maxClusterSessions`，或没有任何组。
- 功能不存在、已通过、已被派出，或同一功能出现在两个组。
- 某功能依赖的功能在另一个组里（提示：放进同一组）。

通过后：
- 不冻结功能清单：规划阶段清单可以反复改、方案可以重新提交，冻结发生在启动那一刻（实现审查后改）。
- 算出冲突提示 `conflicts`：两个 `shared` 组的 `files` 有相同路径，或一个是另一个的目录前缀；主会话自己要做的活（`worktree` 组和没进组的功能）也和各 `shared` 组比较。只提示，不拒绝，由人决定。没写 `files` 的功能记为「范围未知」，同样提示。
- 链记录写 `launchPlan = { proposedAt, proposedBy, groups, note, conflicts }`。重复调用覆盖旧方案。
- 审计 `cluster.proposed`。

### 启动（人操作）

`engine.launchCluster({ chainId, groups? })`，入口是面板按钮（Remote `launchCluster`）和 `/relay launch`。模型没有对应工具。

- 链必须是 `planning` 且有 `launchPlan`，并且没有未解除的阻塞。功能清单在状态转成 `active` 的同一步冻结。传了 `groups` 就是人改过的方案，按 `relay_propose` 的同一套规则再校验一遍。
- `shared` 组：逐组开子会话，复用 `spawn` 的内部逻辑（抽出不要求调用者是模型的那部分）。子会话照旧继承权限预设；计划模式不继承（主会话此时已退出计划模式）。
- 依赖没完成的组先不开（按推荐，实现审查时补）：组里的功能依赖了不在任何组里、且还没通过的功能时，这一组记为「待启动」。前置功能通过后（`relay_checkpoint` 或下一次空闲检查时）插件自动把它开出来，开的是你确认过的同一份方案，不再问一次。常见情形是主会话先做一个地基功能，其余各组等它。
- `worktree` 组：第一期不开会话，功能留给主会话顺序做，结果里标明。
- 某一组开失败：其余组继续；失败组的功能保持未派出，`lastError` 写明哪几组失败。
- 全部处理完：链 `status: 'active'`，写 `launchedAt`，清掉 `launchPlan` 里的待确认状态（保留方案本身供面板回看）。
- 给主会话发监督说明（`renderClusterLaunchedNotice`）：哪些会话领了什么、主会话自己做哪些、子会话回报后要验收。
- 审计 `cluster.launched`。

### 目标（goal）

`clusterGoals` 配置，默认开。（按推荐）
- 启动时，主会话没有 goal 就按链目标建一个，轮次用 `goalRoundsPerHandoff`，记为插件建的（`goalSeeded`）。
- 每个子会话建一个 goal，目标是它领的功能，这样子会话不会跑一轮就停。
- goals 服务不可用时只告警，不影响启动。

### 子会话多开代理

派发提示词现在有一句「不要开链、派生会话或交接」。集群启动的子会话改成：不要开链、不要用 `relay_spawn`；可以用 DSH 的子代理工具把自己的功能再拆开做，结果由自己负责验收和回报。不需要新机制。

### 规划段内的既有行为

- **自动交接**：`evaluate` 只处理 `active` / `initializing`，`planning` 的链不会被自动收尾或交接。已知限制：规划对话特别长时没有接力，靠 `SPEC.md` / `PLAN.md` 落盘兜底。
- **暂停 / 恢复**：`planning` 的链拒绝暂停（恢复会把状态写成 `active`，跳过启动确认）。
- **删除**：`planning` 的链可以删，这就是「取消集群」。
- **`relay_spawn`**：`planning` 的链本来就被拒绝（只允许 `active` / `initializing`）。

### 面板

- 状态标签加 `planning`（规划中）。
- 链列表的卡片带模式标签：集群链显示「集群」，单任务显示「单任务」，不打开详情也能分辨；规划中且已有方案的集群再显示「等你确认启动」。
- 「需要你处理」区：`planning` 且已有启动方案的链列为「等你确认启动」。
- 链详情在 `planning` 时显示「启动方案」卡片：
  - 还没有方案：提示「主会话正在规划」，真理源页签可看 `SPEC.md`、`PLAN.md`。
  - 有方案：卡片顶部一行是摘要（组数、功能数、并行会话数）和实心主按钮「启动 N 个并行会话」，点一次原位变「确认启动 / 取消」，不再用红色危险按钮，也不放在分组列表底部；每组一行，显示标题、功能、AI 给的理由、隔离方式（共用目录 / worktree，后者标「本期由主会话顺序执行」）；冲突提示列在上方；每个功能可改到别的组或新建一组。
- 对话里的启动条：主会话的输入框上方（`conversation.input.dock`，条目 id `relay-launch`）在 `planning` 且有启动方案时显示组数、功能数、各组标题和「启动 N 个并行会话」，同样是两步确认；它按主会话已提交的方案启动，要改分组用旁边的「调整分组」跳到面板。两种入口都调 `remote.launchCluster`，模型仍然没有启动工具。
- 真理源文档加 `SPEC.md` 页签。
- 会话页签「我的任务」在 `planning` 时显示规划中的横幅。

### 配置

| 项 | 默认 | 含义 |
|---|---|---|
| `maxClusterSessions` | `4` | 一次启动最多开几个会话（按推荐；本机内存紧，取保守值） |
| `clusterGoals` | `true` | 启动时给主会话和各子会话建 goal |

## 闭环链

一句话闭环：人输入 `/relay cluster <需求>`，谈完并批准计划后，在主会话输入框上方的启动条或面板的启动方案卡片里点「启动」，随后在接力轨道上看到多个子会话各自领了功能在跑，功能清单逐条变成通过。

| 环 | 发生什么 | 由谁触发或生产 | 正向可观测量 | 失败时谁看得见 |
|---|---|---|---|---|
| 1 入口 | 开集群链，进计划模式 | `lib/command.js::handleRelayCommand`（`cluster`）→ `engine.startCluster` | 面板出现一条「规划中」的链；会话显示计划模式 | 命令返回错误文本 |
| 2 规划 | 模型谈需求、交计划、写三份文件 | 模型，受 `prompts.js::renderClusterPlanningPrompt` 驱动 | `.relay/<链>/SPEC.md`、`PLAN.md` 有内容，`features.json` 有带 `files` 的功能 | 面板卡片一直停在「正在规划」；这一环依赖模型照做，失败是可见但不报错的 |
| 3 提交方案 | 模型提交分组 | `lib/tools.js`（`relay_propose`）→ `engine.proposeCluster` | 链记录有 `launchPlan`；面板卡片出现分组；「需要你处理」多一条 | 工具返回拒绝原因给模型；审计无 `cluster.proposed` |
| 4 人确认 | 人点启动（对话里的启动条或面板卡片顶部） | `client.js` 的 `ClusterLaunchDock` / `LaunchCard` → `lib/remote.js::launchCluster` → `engine.launchCluster` | 审计 `cluster.launched`；链状态变「进行中」 | 面板或启动条显示操作错误；部分组失败时链上有错误文本 |
| 5 并行执行 | 各子会话收到派发说明并开始 | `engine.launchCluster` 内的会话创建与投递 | 接力轨道出现子会话行；DSH 会话列表多出对应会话 | 开失败的组写进链的错误文本和审计 `delegation.failed` |
| 6 回报与验收 | 子会话回报，主会话验收 | 子会话 `relay_checkpoint`；主会话受 `renderClusterLaunchedNotice` 驱动 | 功能清单逐条变成通过并带证据 | 子会话受阻时链上出现阻塞，列入「需要你处理」 |

### 实跑剧本

前置：DSH 已装本插件的新版本，打开一个 git 仓库作为工作区。

1. 基线：打开「长任务接力」面板，记下链的数量。
2. 在会话里输入 `/relay cluster 给这个项目加一个 XXX 功能`。应看到：面板多一条「规划中」的链；会话进入计划模式。
3. 回答模型的提问，直到它提交计划。应看到：DSH 弹出计划评审。点批准。
4. 等模型写完文件。应看到：面板该链的真理源里 `SPEC.md`、`PLAN.md` 有内容；随后出现「启动方案」卡片，列出分组、每组的隔离方式和理由；「需要你处理」里有「等你确认启动」。
5. 把一个功能改到另一组，点「启动」并确认；或者不打开面板，直接在输入框上方的启动条点「启动」并确认。应看到：链状态变「进行中」；接力轨道出现与组数相同的子会话；DSH 会话列表里多出这些会话且各自在运行。
6. 等一个子会话做完。应看到：它领的功能在功能清单里变成通过并带证据。
